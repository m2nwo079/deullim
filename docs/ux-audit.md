# UX 진단 (인터랙션과 정보 구조, 2026-10-24)

운영에 나가는 모든 경로(/console/*, /w, /s, /partners/*)를 대상으로, 이동 구조, 선택 요소의 의미, 누를 수 있는 것의 구분, 정보와 행동의 위계를 살핀다. 시각 디자인(색, 글꼴)은 다루지 않는다. 코드는 고치지 않았다.

- 근거 표시: **코드**는 소스를 읽어 확인한 것, **화면**은 로컬 dev 서버를 띄워 브라우저로 확인한 것이다.
- 화면으로 확인한 범위: 로그인 없이 열리는 화면만이다(콘솔·파트너 로그인, 로그인하지 않은 접근의 이동, 토큰 없는 /w와 /s). 로그인이 필요한 화면은 시연 계정 비밀번호를 쓰지 않으므로 코드로만 확인했다. 휴대폰 폭(390px) 스크린숏은 headless Chrome의 창 최소 폭 때문에 잘려, 폭에 관한 판단에는 쓰지 않았다.
- iOS Safari 동작(뒤로 가기, 새로 고침)은 코드의 기록 처리(history)로 추론한 것이다. 실기기로 확인하지 않았다.
- 예전 docs/ux-issues.md(지금은 없음)의 6개 항목을 아래 발견 목록에 합쳤다(표시: ux-issues).
- 새 UX 문제는 이 문서의 발견 목록에만 더한다. 고치면 해당 행을 지우고 커밋 메시지에 남긴다.

## 1. 화면 계층도

### 지금 실제 이동 관계
콘솔에는 공통 내비게이션이 없다. 콘솔 머리글에는 "들림 콘솔"(링크 아님)과 로그아웃만 있고, ConsoleSidebar 컴포넌트는 docs/components.md에 있지만 쓰이지 않는다. 화면 사이 이동은 개요의 버튼 줄과 각 화면의 "개요" 버튼에 기댄다.

```
/console/login ──로그인──▶ /console (개요)
개요 ─┬▶ 수시 조사 ─┬▶ 수시 조사 시작 ──저장──▶ 수시 조사
      │            └◀ 개요
      ├▶ 개선안 (공정 목록) ──▶ 공정 상세 ─┬▶ 개선안 추가 / 수정 ──저장──▶ 공정 상세
      │      └◀ 개요                       ├▶ 요청 상세 (견적 요청 / 요청 보기)
      │                                    ├▶ (모달) 시연 촬영 QR, 삭제 확인
      │                                    └◀ 공정 목록
      ├▶ 견적 요청 (목록) ──▶ 요청 상세 ─┬▶ 요청 목록, 개선안(공정 상세)
      │      ├▶ 개선안   └◀ 개요          └──삭제──▶ 견적 요청(첫 사업장)
      ├▶ 개선 계획 ──저장──▶ 저장된 계획 ──▶ 개선 계획
      │      ├▶ 개선안 (계획 화면의 "개선안", 결과가 비었을 때 "개선안 입력")
      │      └◀ 개요
      ├▶ 보고서 초안 ──◀ 개요 (글자 링크)
      └▶ QR 관리 ──◀ 개요
/partners/login ──로그인──▶ /partners ──▶ 요청 상세 ──◀ 목록
/w#토큰: 확인 → 작업 선택 → 안내 → 촬영 → 결과 → 통증 신고 → 완료 → 작업 선택
/s#토큰: 확인 → 안내 → 촬영 → 결과
```

- 개요의 공정 표 행에서는 어디로도 갈 수 없다. 위험 공정을 보고 그 공정의 개선안으로 가려면 개요 → 개선안 → 공정을 다시 찾아야 한다(코드).
- 개선 계획, 보고서 초안, QR 관리, 견적 요청 사이는 서로 이어지지 않고, 모두 개요를 거쳐야 한다(코드).

### 바람직한 상위·하위 관계 (제안)
```
콘솔 (머리글: 사업장 선택, 계정)
├ 개요
├ 공정 · 개선안          (개요의 공정 행 → 공정 상세로 바로)
│  └ 공정 상세
│     ├ 개선안 추가 / 수정
│     └ 시연 촬영 (모달)
├ 견적 요청
│  └ 요청 상세
├ 개선 계획
│  └ 저장된 계획
├ 수시 조사
│  └ 수시 조사 시작
├ 보고서 초안
└ QR 관리
```
- 1단계 화면 7개는 모든 콘솔 화면에서 같은 자리(ConsoleSidebar 또는 머리글 탭)로 오간다. 그러면 "개요" 버튼을 화면마다 둘 필요가 없다.
- 사업장 선택은 머리글 한 곳에 두고, 화면 안의 "다른 사업장" 버튼을 없앤다.
- 2단계 이하 화면(공정 상세, 개선안 추가·수정, 요청 상세, 저장된 계획, 수시 조사 시작)은 제목 위에 경로 전체(Breadcrumb)를 같은 모양·자리로 둔다. 마지막 항목은 지금 화면이라 링크가 아니다.

## 3. 발견 목록

심각도: **막음**(작업을 끝낼 수 없음), **헷갈림**(끝낼 수는 있지만 잘못 이해하거나 돌아가야 함), **사소함**.

### 3-1. 이동 구조
| 화면 | 문제 | 관련 컴포넌트 | 심각도 | 근거 |
|---|---|---|---|---|
| /w 안내 | 작업을 잘못 골랐을 때 작업 선택으로 돌아갈 버튼이 없다. 브라우저 뒤로 가기는 /w를 떠나고, 새로 고치면 토큰이 없어 "들어올 수 없는 QR"이 된다. QR을 다시 찍어야 한다 | worker-flow (WorkerTopBar 없음) | 막음 | 코드 |
| /w 전체 | 통증 신고는 촬영 결과 화면에서만 들어갈 수 있다. 아픈 곳만 알리려는 작업자도 30초 촬영을 먼저 해야 한다 | worker-flow | 막음 | 코드 |
| /w, /s 전체 | 단계가 화면 안의 상태라 iOS Safari의 뒤로 가기(가장자리 밀기 포함)가 흐름을 통째로 떠나고, 돌아와도 토큰이 없어 처음부터 다시 해야 한다 | worker-flow, simulation-flow | 헷갈림 | 코드 |
| 콘솔 전체 | 공통 내비게이션이 없다. 계획 → 보고서, 보고서 → 견적 요청처럼 자주 오가는 이동도 개요를 거친다 | ConsoleSidebar(문서에만 있음) | 헷갈림 | 코드 |
| 개요 | 공정 표의 행이 어디로도 이어지지 않는다. 위험 공정에서 그 공정의 개선안으로 바로 갈 수 없다 | DataTable | 헷갈림 | 코드 |
| 요청 상세 | 초안을 지우면 사업장 없이 요청 목록으로 가서, 다른 사업장의 요청이었으면 첫 사업장 목록이 보인다 | requests/actions.ts | 헷갈림 | 코드 |
| 개선 계획 | 저장하면 저장된 계획 화면으로 넘어가고, 뒤로 가기로 돌아오면 입력한 예산과 계산 결과가 사라진다 | plan-screen | 사소함 | 코드 |
| 개선 계획 | 새로 계산한 결과를 저장된 계획과 견주려면 저장된 계획 화면을 따로 열어야 한다(ux-issues) | 개선 계획 화면 | 헷갈림 | 코드 |
| 보고서 초안 | "개요"가 다른 화면과 달리 글자 링크(왼쪽 화살표)다 | Link, ButtonLink | 사소함 | 코드 |

### 3-2. 선택 요소
| 화면 | 문제 | 관련 컴포넌트 | 심각도 | 근거 |
|---|---|---|---|---|
| 콘솔 6개 화면 | 사업장 선택이 화면마다 다르다. 개요는 머리글 줄의 "사업장 바꾸기" 묶음, 보고서는 체크 표시가 붙는 칩, 나머지(수시 조사, 개선안, 견적 요청, 개선 계획, QR 관리)는 "개요" 같은 이동 버튼 사이에 다른 사업장 이름의 버튼만 놓는다. 지금 사업장은 버튼이 아니라 작은 글자로만 보인다 | ButtonLink | 헷갈림 | 코드 |
| 보고서 초안 | 사업장과 "함께 넣을 개선 계획"은 하나만 고르는 선택인데, 링크 버튼 묶음으로 만들고 고른 것은 체크 아이콘으로만 구분한다. 버튼처럼 보여 누르면 무슨 일이 생기는지(화면이 바뀜) 알기 어렵다 | ButtonLink(aria-current) | 헷갈림 | 코드 |
| 시연 QR 창 | 단위작업 선택에서 선택됨과 초점이 구분되지 않고, 글자 입력칸처럼 보인다(ux-issues) | SegmentedControl (choice-field.tsx) | 헷갈림 | 코드 |
| 견적 요청 상세 (초안) | 희망 기한 달력이 선택할 수 있는 마지막 날(2년 뒤)을 "오늘"로 표시하고(테두리, aria-current="date"), 값이 비면 2년 뒤 달에서 열린다. 저장 날짜는 어긋나지 않는다(ux-issues) | DateField | 헷갈림 | 코드 |
| 견적 요청 상세, 수시 조사 | 1000자 설명과 500자 메모를 한 줄 입력칸에 적는다(ux-issues) | TextField(여러 줄 입력 없음) | 헷갈림 | 코드 |

### 3-3. 누를 수 있는 것의 구분
| 화면 | 문제 | 관련 컴포넌트 | 심각도 | 근거 |
|---|---|---|---|---|
| 개요 | 기한·검토 알림 안의 이동은 글자 링크("수시 조사 보기", "검토하기")이고, 같은 화면의 다른 이동은 버튼이다. 같은 일(다른 화면으로 가기)이 두 모양이다 | InlineAlert(action), ButtonLink | 사소함 | 코드 |
| 콘솔 전체 | 화면 이동(ButtonLink)과 그 자리의 동작(Button)이 같은 secondary 모양이다. 요청 상세 머리글에서는 "요청 목록", "개선안"(이동)과 "삭제", "수락 없이 마감"(되돌릴 수 없는 동작)이 한 줄에 같은 모양으로 놓인다 | Button, ButtonLink | 헷갈림 | 코드 |

| QR 관리 | 행마다 재발급, 기간 연장, 비활성화가 같은 모양으로 붙어 있다. 비활성화는 되돌릴 수 없다(확인 창은 있다) | DataTable(action 열), Button | 사소함 | 코드 |
| / (첫 화면) | 이름과 문구만 있고 콘솔·파트너로 가는 길이 없다 | — | 사소함 | 코드 |

### 3-4. 위계
| 화면 | 문제 | 관련 컴포넌트 | 심각도 | 근거 |
|---|---|---|---|---|
| 개요 | 주 버튼이 없다. 화면 이동 버튼 6개가 같은 무게로 나란하고, 위험 공정이나 기한 알림에서 이어질 행동이 두드러지지 않는다 | ButtonLink, StatStrip, InlineAlert | 헷갈림 | 코드 |
| 개선 계획 | 결과가 나온 뒤에도 "계산"이 주 버튼이고, 이 화면의 결과물인 "저장"은 보조 버튼이다 | plan-screen, Button | 헷갈림 | 코드 |

### 3-5. 휴대폰 예외 상태 (/w, /s)
첫 진단에서는 이동·선택·위계만 보고 예외 상태는 조사하지 않았다. 아래는 그 뒤 코드로 확인한 것이다. 실기기로 확인하지 않았다.

| 화면 | 상태 | 지금 동작 | 문제 | 심각도 | 근거 |
|---|---|---|---|---|---|
| /w, /s 촬영 | 카메라 권한 거부 | "브라우저 설정에서 카메라 권한을 허용한 뒤 다시 시도해 주세요." + "다시 시도"(안내로) | iOS Safari는 한 번 거부하면 사이트 설정(주소창 aA → 웹사이트 설정 → 카메라)을 바꾸기 전까지 다시 시도해도 계속 거부된다. 어디서 바꾸는지 알려 주지 않는다 | 막음 | 코드 |
| /w, /s 촬영 | 카메라를 다른 앱이 쓰는 중, 조건 불일치 | 권한 거부가 아닌 오류는 모두 "카메라를 찾을 수 없어요" | 카메라가 있는데 "찾을 수 없다"고 안내한다(NotReadableError 등을 구분하지 않음) | 헷갈림 | 코드 |
| /w, /s 촬영 | 자세 분석 모델을 못 받음 | "인터넷 연결을 확인하고 다시 시도" + "다시 시도" | 문제 없음 | — | 코드 |
| /w, /s 보내는 중 | 결과 계산·저장 | 가운데 글자 "결과를 계산하고 있어요."(aria-live)만 | 진행 표시가 없고 요청에 시간 제한이 없어, 망이 멈추면 이 화면에 계속 머문다. 취소나 다시 보내기가 없다. QR 확인 중("QR을 확인하고 있어요.")도 같다 | 헷갈림 | 코드 |
| /w, /s 보내기 실패 | 망 오류, 서버 오류 | "결과를 보내지 못했어요" + "다시 보내기"(같은 좌표를 다시 보냄) / "다시 찍기" | 문제 없음. 좌표는 화면 메모리에만 있어 새로 고치면 사라진다는 안내는 없다 | 사소함 | 코드 |
| /w, /s 보내기 | 자세가 잘 보이지 않음(422) | 안내 + "다시 찍기" | 문제 없음 | — | 코드 |
| /w 결과 | 시간당 저장 한도(429) | 결과는 보여 주고 "저장되지 않았어요" 안내 | 문제 없음 | — | 코드 |
| /w, /s 도중 | 토큰이 비활성화·만료·사용됨(401) | "들어올 수 없는 QR이에요" / "쓸 수 없는 시연 QR이에요" | 촬영한 결과가 사라지는 이유를 알 수 있다. 문제 없음 | — | 코드 |
| /w 통증 신고 | 보내는 중, 실패, 한도(429), 토큰 무효 | 버튼 처리 중 표시, 입력 비활성, 실패 문구는 버튼 위, 401은 무효 화면 | 문제 없음 | — | 코드 |

## 4. 확정한 규칙
규칙 초안은 검토를 거쳐 docs/components.md에 옮겼다("위험한 동작", "이동", "버튼 위계", "선택 요소", "상태 표시" 절과 목록 표). 화면 폭 기준은 docs/design-tokens.md 4.4(screen-sm 640px, screen-lg 1024px)에 있다. 초안에서 바뀐 결정은 다음과 같다.

- 견적 수락은 위험한 동작이 아니라 견적 비교 화면의 주요 결정이다. 행마다 수락 버튼을 두지 않고, DataTable 선택 열(radio)로 하나를 고른 뒤 주요 버튼 "선택한 견적 수락"(확인 창 유지)으로 수락한다. accept_quote는 고른 견적의 가격과 수정 시각을 그대로 받는다.
- 위험한 동작은 빨간색 없이(위험도 색 규칙) 줄 끝 배치와 간격으로 떼고, 확인 버튼에 동작과 대상을 함께 적는다.
- Breadcrumb는 상위 링크 하나가 아니라 경로 전체를 보여 주고, 마지막 항목(지금 화면)은 링크가 아니다.
- 이동 뒤 결과는 주소에 결과 코드만 넘기고 문구는 도착 화면이 고른다.
- "보내는 중" 15초 뒤에는 "연결이 느려요"만 더해 보여 준다. 다시 보내기는 같은 촬영이 두 번 저장되지 않는 방법(다시 시도를 여는 시점, 또는 요청 고유값)을 5단계에서 저장 함수 구조를 보고 정한 뒤에 둔다.
- 통증 신고만 하는 입구는 QR 첫 화면에 둔다(5단계). DB와 API는 바꾸지 않는다.
