# 인증과 권한 (v1)

## 사용자별 방식
| 사용자 | 방식 | 비고 |
|---|---|---|
| 관리자 (manager) | Supabase Auth 이메일 + 비밀번호 | 셀프 가입 없음. 운영자가 계정을 만들고 소속 사업장을 연결한다 |
| 파트너 (partner) | Supabase Auth 이메일 + 비밀번호 | 셀프 가입 없음. 운영자가 계정을 만들고 소속 회사를 연결한다 |
| 작업자 | 계정 없음. QR의 작업장 토큰으로 접근 | Supabase 익명 로그인도 쓰지 않는다 |

- Google 로그인은 MVP에서 쓰지 않는다. 필요하면 이후 추가한다.
- Supabase 무료 플랜의 기본 이메일 발송 한도는 확인하지 않았다. 셀프 가입과 이메일 인증을 쓰지 않으므로 MVP 영향은 작을 것으로 본다.

## 작업자 흐름
1. QR에는 작업장별 무작위 토큰이 들어 있는 주소가 담긴다. 형식은 `https://<사이트>/w#<토큰>`이다.
   토큰은 URL 프래그먼트에 두어 서버 로그, Referer, 쿼리에 남지 않게 한다. 작업자 화면은 location.hash를 읽어
   주소창에서 지운 뒤(history.replaceState) Route Handler에 POST 본문으로 보낸다.
   토큰 원문은 32바이트 무작위 값을 base64url로 바꾼 43자이며, 발급 직후 한 번만 화면에 보이고 DB에는 SHA-256 해시만 저장한다.
2. 작업자가 접속하면 Route Handler가 토큰을 해시해 entry_tokens와 비교하고, active와 expires_at을 확인한다.
3. 유효하면 촬영 결과(관절 좌표)와 신고를 받아 서버 권한으로 저장한다. 작업자 브라우저는 DB에 직접 접근하지 않는다.
   촬영 결과는 서버가 tasks의 관리자 입력과 받은 관절 좌표로 점수를 다시 계산해 저장하며, 원본 좌표는 저장하지 않는다.
4. 신고와 촬영 저장은 report_rate_limits로 토큰별 시간당 건수를 제한한다(신고 20건, 촬영 저장 10건, 정시 기준 고정 창).
   IP 주소, 기기 식별자, 쿠키 기반 식별자는 저장하지 않는다.
5. 토큰이 유출되었으면 관리자가 콘솔에서 비활성화하고 새 QR을 발급한다.

## 시연 촬영 흐름
1. 관리자가 콘솔의 개선안 상세에서 개선안과 단위작업을 고르면, 서버가 일회용 토큰을 만들어 `https://<사이트>/s#<토큰>` QR을 보여 준다.
   토큰 형식과 프래그먼트 처리는 작업자 QR과 같고, DB에는 SHA-256 해시만 저장한다(simulation_tokens).
2. 휴대폰은 로그인 없이 이 QR로 들어온다. Route Handler가 토큰을 해시해 확인하고 개선안·공정·단위작업 이름만 돌려준다.
3. 촬영 결과(관절 좌표)를 받으면 서버가 그 단위작업의 관리자 입력으로 다시 계산하고, 저장에 성공하면 토큰을 다시 쓸 수 없게 한다. 원본 좌표와 영상은 저장하지 않는다.
4. 토큰은 15분 유효하고 한 번만 쓴다. 발급은 관리자당 시간당 20개까지다. 기존 작업자 QR 토큰으로는 시연 촬영을 할 수 없다(작업자가 개선안 효과를 바꾸지 못하게 하기 위해서다).
- /s는 web/proxy.ts의 대상(/console 아래)이 아니며 세션을 만들지 않는다.

- 익명 로그인을 쓰지 않는 이유: 익명 로그인도 기기마다 사용자 ID를 만들어, 신고 기록과 연결되면 같은 사람의 반복 신고가 드러날 수 있다.

## 권한 강제
- 1차: DB의 Row Level Security. 관리자는 소속 사업장, 파트너는 공개된 요청과 자기 회사 견적만 읽는다 (docs/data-model.md 권한 표).
- 2차: secret key(`SUPABASE_SECRET_KEY`)를 쓰는 Route Handler는 요청한 사용자의 역할과 소속을 코드에서 직접 확인한다.
- secret key(`SUPABASE_SECRET_KEY`)는 web/src/lib/supabase/admin.ts에서만 참조하고, 이 파일은 서버 전용이다 (docs/lint-rules.md L4, L5).
- 화면 분기만으로 권한을 처리하지 않는다.

## 세션
- 관리자와 파트너의 세션은 Supabase Auth의 기본 방식을 따른다. Next.js에서의 쿠키 처리 방식은 스캐폴딩 때 Supabase 공식 문서로 확인한다.
- 작업자에게는 세션을 만들지 않는다. 요청마다 토큰을 확인한다.
- 콘솔 경로: 로그인 `/console/login`, 개요 `/console`. 로그인 후 돌아갈 주소는 같은 사이트의 `/console` 아래 경로만 허용한다.
- 들림 파트너스 경로: 로그인 `/partners/login`, 요청 목록 `/partners`, 요청 `/partners/requests/<id>`. 로그인 후 돌아갈 주소는 `/partners` 아래 경로만 허용한다.
  partner가 아닌 계정(관리자 포함)은 로그인 직후 로그아웃시키고, 레이아웃과 각 페이지도 서버에서 다시 막는다. 관리자가 견적을 쓰는 것은 DB 정책(파트너 소속 확인)도 막는다.
- web/proxy.ts가 `/console`과 `/partners` 아래에서 세션을 갱신하고, 로그인하지 않은 사용자를 그 경로의 로그인 화면으로 보낸다. 최종 확인은 콘솔 레이아웃과 각 페이지가 서버에서 다시 한다.
- 로그인 실패 문구는 계정 존재 여부가 드러나지 않게 하나로 통일한다.
  요청 제한(429), 서버 오류, 네트워크 실패는 "잠시 후 다시 시도" 문구로 따로 안내한다. 관리자가 맞는 비밀번호를 반복 입력하지 않게 하기 위해서다.
- manager가 아닌 계정(파트너 등)은 로그인 직후 로그아웃시키고 콘솔에 들어올 수 없다고 안내한다.

## 시연 준비
- 관리자 1개, 파트너 1개의 시연용 계정을 운영 프로젝트에 미리 만든다. 비밀번호는 커밋하지 않는다.
- 시연용 사업장, 공정, QR 토큰을 미리 만든다.

## 확정
- 토큰 만료 기간: 90일, 관리자가 기간 연장(같은 QR 유지). 연장하면 지금부터 90일 뒤로 바뀐다. 비활성화된 토큰은 연장할 수 없다
- 만료된 토큰도 비활성화되지 않았다면 기간 연장으로 다시 쓸 수 있다. 유출이 의심되면 비활성화한다.
