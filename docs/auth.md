# 인증과 권한 (v1)

## 사용자별 방식
| 사용자 | 방식 | 비고 |
|---|---|---|
| 관리자 (manager) | Supabase Auth 이메일 + 비밀번호 | 셀프 가입 없음. 운영자가 계정을 만들고 소속 사업장을 연결한다 |
| 파트너 (partner) | Supabase Auth 이메일 + 비밀번호 | 셀프 가입 없음. 운영자가 계정을 만들고 소속 회사를 연결한다 |
| 작업자 | 계정 없음. QR의 작업장 토큰으로 접근 | Supabase 익명 로그인도 쓰지 않는다 |

- Google 로그인은 MVP에서 쓰지 않는다. 필요하면 이후 추가한다.
- Supabase 무료 플랜의 기본 이메일 발송 한도는 확인하지 않았다. 셀프 가입과 이메일 인증을 쓰지 않으므로 MVP 영향은 작을 것으로 본다.

## 작업자 흐름
1. QR에는 작업장별 무작위 토큰이 들어 있는 주소가 담긴다.
2. 작업자가 접속하면 Route Handler가 토큰을 해시해 entry_tokens와 비교하고, active와 expires_at을 확인한다.
3. 유효하면 촬영 결과(관절 좌표)와 신고를 받아 서버 권한으로 저장한다. 작업자 브라우저는 DB에 직접 접근하지 않는다.
4. 신고는 report_rate_limits로 토큰별 시간당 건수를 제한한다. IP 주소, 기기 식별자, 쿠키 기반 식별자는 저장하지 않는다.
5. 토큰이 유출되었으면 관리자가 콘솔에서 비활성화하고 새 QR을 발급한다.

- 익명 로그인을 쓰지 않는 이유: 익명 로그인도 기기마다 사용자 ID를 만들어, 신고 기록과 연결되면 같은 사람의 반복 신고가 드러날 수 있다.

## 권한 강제
- 1차: DB의 Row Level Security. 관리자는 소속 사업장, 파트너는 공개된 요청과 자기 회사 견적만 읽는다 (docs/data-model.md 권한 표).
- 2차: secret key(`SUPABASE_SECRET_KEY`)를 쓰는 Route Handler는 요청한 사용자의 역할과 소속을 코드에서 직접 확인한다.
- secret key(`SUPABASE_SECRET_KEY`)는 web/src/lib/supabase/admin.ts에서만 참조하고, 이 파일은 서버 전용이다 (docs/lint-rules.md L4, L5).
- 화면 분기만으로 권한을 처리하지 않는다.

## 세션
- 관리자와 파트너의 세션은 Supabase Auth의 기본 방식을 따른다. Next.js에서의 쿠키 처리 방식은 스캐폴딩 때 Supabase 공식 문서로 확인한다.
- 작업자에게는 세션을 만들지 않는다. 요청마다 토큰을 확인한다.

## 시연 준비
- 관리자 1개, 파트너 1개의 시연용 계정을 운영 프로젝트에 미리 만든다. 비밀번호는 커밋하지 않는다.
- 시연용 사업장, 공정, QR 토큰을 미리 만든다.

## 확정
- 토큰 만료 기간: 90일, 관리자가 수동 갱신

## 미결정
- 비밀번호 정책 (Supabase 기본값 사용 여부)
